# T04：Conflict 衝突發生的處理

> 所屬階段：[回到第一階段：建立與取得 Repo](README.md) · [課程總覽](../../README.md)

## 任務目標

在 T03，我們學會了用 Push 和 Pull 同步版本。有時 Pull 時，Git 會告訴我們發生了 Conflict（衝突）。別擔心，這不代表你的工作消失了，而是 Git 需要你幫忙決定最後要保留哪些內容。

這一課，老師會帶你了解衝突為什麼發生、親手在測試儲存庫中製造一個簡單的例子，再用 VS Code 完成處理。最後也會整理一套平常工作的好習慣，幫助我們減少衝突。

## 學習重點

- **什麼是衝突**：當 Git 要整合不同的修改，卻無法確定應該保留什麼內容時，會暫停並請我們協助處理。
- **為什麼會發生**：例如兩個人各自修改了同一個檔案的同一行；或一邊刪除檔案，另一邊卻修改了它。修改同一個檔案不一定會衝突，Git 能自動整合不同位置的許多修改。
- **怎麼處理**：先看懂兩邊的修改，再決定保留其中一邊、兩邊合併，或手動整理成正確內容。檢查結果、儲存並暫存後，還要完成這次整合的 Commit。
- **先 Pull 的好處**：開始工作前先取得遠端更新，可以減少在舊版本上修改的機會。但你工作期間，別人仍可能更新相同內容，所以無法完全避免衝突。

### 用作業來想一想

小明和小華各自拿到同一份作業，原本都寫著「繳交日期：星期五」。小明把日期改成「星期四」，小華則改成「星期六」。當他們想把兩份修改整合起來時，電腦無法替他們決定正確日期，這時就需要他們討論並選擇。

Git 遇到相似情況也會請你協助。重點不是隨便選一邊，而是先理解修改內容，必要時和協作者確認。

## 實作練習

### 開始之前

請先完成 [T00](T00-註冊Github與設定VSCode.md)、[T01](T01-建立一個儲存庫.md)、[T02](T02-提交Commit一個版本.md) 和 [T03](T03-推送至遠端Push與從遠端拉取Pull.md)。這次要刻意製造衝突，請使用**自己有寫入權限的測試儲存庫**，不要用正式專案或他人的工作練習。

在 VS Code 開啟已連接 GitHub 的測試儲存庫，並在 <a href="https://github.com/" target="_blank" rel="noopener noreferrer">GitHub 網頁</a>開啟同一個儲存庫。這次練習請維持 T03 使用的工作位置，不要切換；也請先確認 **Source Control**（原始檔控制）沒有未提交的修改，先前的提交已推送且兩邊內容一致。若有未完成的工作，先妥善保留；不確定時請老師協助。

### 1. 準備共同的作業版本

1. 在 VS Code 的檔案總管新增 `conflict-practice.md`。如果已經有同名檔案，請改用一個尚不存在的檔名，並在後續步驟使用同一個名稱，不要覆寫原有檔案。
2. 輸入以下內容並儲存：

   ```text
   繳交日期：星期五
   ```

3. 在 **Source Control** 檢查並暫存這個檔案，以 `新增衝突練習檔案` 為訊息 Commit，再選擇 **... → Push**（更多動作 → 推送）。
4. 在 GitHub 網頁確認同一個儲存庫中看得到這個檔案，內容是「繳交日期：星期五」。如果 Push 失敗，請先停下來閱讀提示；不要使用 Force Push（強制推送）或繼續製造衝突。

### 2. 製造一個衝突

接下來我們先在網頁修改一次，再回到 VS Code 修改**同一行**，模擬兩個人從相同版本各自工作。

1. 在 GitHub 網頁打開 `conflict-practice.md`，點選鉛筆圖示編輯，將「星期五」改成「星期六」。依 T02 的網頁提交方式，以 `網頁修改繳交日期` 為訊息提交。確認網頁上顯示「繳交日期：星期六」。
2. 回到 VS Code，**先不要 Pull**。開啟本機的 `conflict-practice.md`，確認仍是「繳交日期：星期五」，將它改成「繳交日期：星期四」並儲存。
3. 在 **Source Control** 檢查、暫存這個檔案，以 `本機修改繳交日期` 為訊息 Commit。現在本機和 GitHub 各自修改了同一行。
4. 確認沒有其他尚未提交的修改後，在 VS Code 選擇 **Terminal → New Terminal**（終端機 → 新增終端機），確認終端機位於這個測試儲存庫，輸入：

   ```sh
   git pull --no-rebase
   ```

   這個指令會取得並嘗試合併遠端更新。這次的同一行修改應該會造成衝突，Git 會暫停合併，等待我們處理。若沒有出現衝突，先確認網頁和本機修改的是相同的檔案、同一行，以及兩邊是否使用同一個儲存庫；不要重複建立提交。

### 3. 在 VS Code 處理衝突

1. 回到 **Source Control**，在 **Merge Changes**（合併變更）中找到 `conflict-practice.md` 並開啟。介面名稱和顯示方式可能因 VS Code 版本而不同。
2. 如果看到衝突標記，內容會類似下面這樣（標記後的名稱可能不同）：

   ```text
   <<<<<<< HEAD
   繳交日期：星期四
   =======
   繳交日期：星期六
   >>>>>>> 遠端版本
   ```

   `<<<<<<<` 到 `=======` 之間是這次 Pull 合併時的本機內容；`=======` 到 `>>>>>>>` 之間是這次取回的遠端內容。請先看懂兩邊，再決定結果。
3. 編輯器若顯示 **Accept Current Change**（接受目前變更）、**Accept Incoming Change**（接受傳入變更）和 **Accept Both Changes**（接受兩邊變更），可以用它們選擇要保留的內容。這次假設確認後要改成「繳交日期：星期日」，請手動將衝突區塊整理成這一行，並移除衝突標記。
4. 如果看到的是合併編輯器，請比較 **Current**（目前內容）與 **Incoming**（傳入內容），在 **Result**（結果）中整理成「繳交日期：星期日」。確認沒有未處理的衝突後，選擇 **Complete Merge**（完成合併編輯）；這會完成並暫存該檔案，**不等於**完成整個儲存庫的合併。
5. 不論使用哪種方式，都請檢查整個檔案：確認結果正確、沒有重複內容或 `<<<<<<<`、`=======`、`>>>>>>>` 標記，然後儲存。若使用一般編輯器，回到 **Source Control**，點選檔案旁的 **+**（Stage Changes，暫存變更）；若使用合併編輯器，確認檔案已出現在 **Staged Changes**（已暫存的變更）。
6. 如果還有其他衝突檔案，也要逐一處理並暫存。這個練習應只有一個衝突檔案；若出現未預期的內容，先停下來請老師協助。確認所有衝突都已處理後，在 **Source Control** 檢查暫存內容，使用顯示的合併訊息或輸入 `整合繳交日期修改`，按 **Commit** 完成這次合併。
7. 在終端機輸入 `git status`，確認沒有未解決的衝突，也沒有顯示合併仍在進行。接著選擇 **... → Push**，將完成的提交上傳；回到 GitHub 網頁，確認檔案顯示「繳交日期：星期日」。

如果 Git 提示無法提交或推送，先看清楚錯誤訊息並確認所有衝突都已處理；不確定時先請老師協助，不要直接丟棄修改或強制推送。本練習使用的是 Pull 合併；其他操作造成衝突時，完成方式可能不同。

### 4. 減少衝突的工作習慣

日常使用 VS Code 和 GitHub 時，老師建議依照這個順序工作：

1. **開始修改前，Fetch／Pull**：確認開啟的是正確儲存庫，先妥善保留未完成的工作。**Fetch**（擷取）只取得遠端更新資訊，不會更新目前檔案；確認更新後，使用 **Pull** 取得並整合到本機。在 VS Code 的 **Source Control** 可從 **... → Fetch** 和 **... → Pull** 操作。
2. **開始修改**：在本機編輯程式或文件；協作時，可以先和同學確認各自負責的內容。
3. **Save → Stage → Commit**：儲存檔案、檢查並選擇要暫存的修改，再建立一個有清楚訊息的版本。
4. **Push**：將已提交的版本上傳到 GitHub。若 Push 被拒絕，先確認遠端更新並妥善保留工作，再整合後重新推送；不要強制覆蓋。

這樣能減少在舊版本上工作的機會，但不能保證完全沒有衝突：別人可能在你開始修改後才上傳變更。遇到衝突時，慢慢檢查並與協作者確認就好。
